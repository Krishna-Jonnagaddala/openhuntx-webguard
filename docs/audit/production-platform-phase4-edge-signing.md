# Production Platform, Phase IV: Edge, Signing, and Deployment Readiness (Slice 18)

## 0. Scope confirmation

Slice 14 decided TrustScan's production signing custody (`docs/production/TRUSTSCAN_PRODUCTION_SIGNING.md`, Option A: CloudHSM-backed Ed25519) but explicitly did not authorize implementation. Slices 12/17 built PostgreSQL, KMS-key IaC, object storage, and transactional email, but left the entire public-facing edge (Cloudflare, TLS, reverse proxy, WAF) as design-only (`docs/production/INFRASTRUCTURE_REQUIREMENTS.md`'s "Web/API (public-facing)" and "Callback service" sections). This slice closes both: it implements the CloudHSM signing architecture Slice 14 decided, and it produces the first reviewed public-edge model (Cloudflare/TLS/WAF/rate-limiting/origin-protection) this project has had. Scanner v1 detector logic was not touched; no vulnerability detector was added; the WebGuard application was not redesigned. Every change below is infrastructure, signing custody, edge configuration, or test/documentation work.

**Deployment status, stated once, precisely, and true for every section below**: nothing in this slice was deployed. No CloudHSM cluster, no Cloudflare account, no DNS zone, and no load balancer were created. `infra/terraform/` is reviewed, `fmt`/`init`/`validate`-clean, and never applied.

## 1-4. TrustScan production signing, signing service, key lifecycle, signing E2E (requirements 1-4)

Full detail: `docs/production/TRUSTSCAN_SIGNING_SERVICE.md`. Summary:

- `CloudHsmSigningProvider` (`signing.py`) implements `SigningProvider` over an injected `Pkcs11Ed25519KeyProtocol`: same Ed25519 contract, same `key_id` derivation, zero permit-schema change, exactly as Slice 14's decision required.
- A dedicated `TrustScan Signing Service` (`signing_service.py`, run via `webguard-api signing-service`) stands between every API/worker process and CloudHSM. Its HTTP surface is exactly three endpoints mirroring `SigningProvider` (`POST /v1/sign`, `GET /v1/active-key-id`, `GET /v1/public-key/{id}`); `SigningServiceHandlerTests` in `tests/unit/test_cloudhsm_signing.py` proves `/v1/encrypt`, `/v1/decrypt`, `/v1/keys`, `/v1/rotate`, `/v1/disable` all 404. Neither the API nor the worker process holds a PKCS#11 session or CloudHSM credential in this architecture (requirement 2).
- Key lifecycle (active/retired/disabled, rotation, verification against retired keys, emergency disable) is entirely the pre-existing `SigningKeyRegistry` (Slice 12); this slice adds a new provider it can hold, not new lifecycle machinery. Raw private-key material never leaves CloudHSM; the PKCS#11 adapter only ever holds a handle.
- E2E proof (requirement 4): `tests/integration/test_signing_service_e2e.py`, against real PostgreSQL, through the full production-component-assembly path (`build_production_components`): a permit is signed by a real, running `SigningServiceServer` over real HTTP, a job consumes it, the worker verifies it and produces a signed Safety Receipt. **This proves the service boundary and HTTP wiring end-to-end against a real database; it does not and cannot prove real CloudHSM signing**, since the harness backs the signing service with `LocalDevelopmentSigner`, not a real HSM: no cluster or PKCS#11 driver is available in this environment. Stated with no hedging: real CloudHSM validation has not happened.

## 5-9. Public domain model, reverse proxy/ingress, TLS, Cloudflare/WAF, origin protection (requirements 5-9)

Full detail: `docs/production/PUBLIC_EDGE_SECURITY.md`. Summary:

- Three environment-driven hostnames (`app.`/`api.`/`callback.openhuntx.com`), no DNS name assumed to exist. `infra/terraform/cloudflare.tf` provisions the zone, proxied DNS records, `ssl = "strict"`/`min_tls_version = "1.2"`/`tls_1_3 = "on"`/`always_use_https = "on"` zone settings, a managed-WAF-ruleset execution, a byte-exact request-size firewall rule (131072 bytes, matching `MAXIMUM_API_REQUEST_BYTES` precisely), a three-rule edge rate-limit ruleset, and `cloudflare_authenticated_origin_pulls_settings`.
- The reverse-proxy/ingress path is stated precisely, including a real, pre-existing constraint this slice did not remove: `production_config.py`'s `ProductionServiceConfig` still hard-rejects a non-loopback API bind (`production_config_non_loopback_binding_rejected`), so the path is `Internet -> Cloudflare -> load balancer -> host-local TLS-terminating reverse-proxy sidecar -> API process (127.0.0.1)`, not a direct LB-to-process path. This is named explicitly rather than left implicit, since it is a real requirement on how an operator must implement requirement 6.
- Cloudflare provider schema (v5.24.0) was verified via the provider's own published documentation and cross-checked against a real-world, actively-maintained configuration using the identical managed-ruleset IDs (`efb7b8c949ac4650a09736fc376e9aee`, `4814384a9e5d4991b9815dcfc25d2f1f`), not guessed. `terraform providers schema -json` (queried directly against the locally-installed provider) was used to get exact `aws_cloudhsm_v2_cluster`/`aws_cloudhsm_v2_hsm` attribute names, avoiding any speculative schema.
- Origin protection is authenticated origin pulls as the primary control (Cloudflare presents a client certificate the origin must verify) plus Cloudflare-IP allow-listing named as a complementary, not replacement, second layer.

## 10. API request limits (requirement 10)

`docs/production/PUBLIC_EDGE_SECURITY.md` §5's table is the full answer: every edge limit is deliberately looser than its application-level counterpart, so the application (which has real per-account state) remains the actual abuse-decision authority; the edge exists only to blunt a volumetric flood before it reaches the origin. The request-body bound is not just "complementary" but numerically identical at both layers (131072 bytes): the edge can never reject something the application would accept, or the reverse. This also closes a real, previously-named gap: `INFRASTRUCTURE_REQUIREMENTS.md`'s "Web/API (public-facing)" section named `FixedWindowRateLimiter`'s per-instance nature as a scaling limitation; Cloudflare's edge rules are evaluated centrally across every origin instance, giving a genuine cross-instance-shared bound the application alone cannot.

## 11. Browser security headers, validated against the real built frontend (requirement 11)

`apps/web` was built for real (`npm run build`) and `dist/index.html` inspected directly: no inline script/style, every asset same-origin, the only external dependency is the API base URL, confirming a strict SPA CSP is genuinely achievable (documented in `PUBLIC_EDGE_SECURITY.md` §7). The API's own headers were checked against a real running server configured exactly as production would be (`secure_cookies=True`, `hsts_enabled=True`, a real `allowed_origins`, a real trusted-proxy CIDR), not by code review alone. CORS was verified the same way: a request from the configured origin gets a correct grant, a request from `https://evil.example` gets **no** `Access-Control-Allow-*` header at all. CSP was not weakened anywhere to make anything work: `default-src 'none'` on the JSON API is correct, not loosened.

## 12. Cookie validation behind a proxy (requirement 12)

Three new tests, `tests/unit/test_customer_auth.py::SecureCookieAttributesTests`: the first tests in this codebase to exercise `secure_cookies=True` at all (every pre-existing cookie test used the dev-mode `False` default). Proven directly: `wg_session` gets `Secure`+`HttpOnly`+`SameSite=Lax`+`Path=/`; `wg_csrf` gets `Secure`+`SameSite=Lax`+`Path=/` and deliberately **not** `HttpOnly` (the double-submit pattern needs it script-readable); logout clears both while still marking them `Secure`. No `Domain` attribute is ever set (host-only cookies, a reviewed choice given `app.`/`api.openhuntx.com` are different origins). Proxy-HTTPS-awareness: `secure_cookies` is a static operator-set flag, never derived from `X-Forwarded-Proto`, a deliberate design (deriving it from a spoofable forwarding header would be exactly the "blindly trusting attacker-controlled forwarding headers" requirement 12 warns against), unchanged by this slice, now proven under `True` for the first time.

## 13. Trusted proxy handling (requirement 13)

`http_api.py`'s `_resolve_client_ip()`: `CF-Connecting-IP`/`X-Forwarded-For` are honored only when the direct TCP peer is itself inside a configured `trusted_proxy_networks` CIDR set (empty by default; every pre-Slice-18 deployment's behavior is unchanged). This resolved IP feeds every rate-limit bucket key and every audit `ip_address` field, not a subset. Proven by `tests/unit/test_trusted_proxy.py` (5 tests, real HTTP against a real running server): headers ignored and shared-bucket by default; `CF-Connecting-IP` honored and per-claimed-IP-bucketed once trusted; `X-Forwarded-For` leftmost-entry fallback; `CF-Connecting-IP` priority over `X-Forwarded-For`; a malformed header falls back to the real (rate-limited) peer.

## 14-15. Callback hostname design and service isolation (requirements 14-15)

Full detail: `docs/production/CALLBACK_SERVICE_DEPLOYMENT.md`. Summary: `callback.openhuntx.com` is prepared as its own distinct Cloudflare origin (not a path under `api.`), `CallbackHttpReceiver` gained an optional per-IP rate limiter protecting its own correlation-store writes (a rate-limited request gets the identical generic response as a recorded one, no oracle), and `webguard-api callback-service` runs it as a fully independent process from the API/worker. Every pre-existing safety property (token-only correlation, uniform generic responses, bounded observation storage) is preserved, not loosened, by this preparation.

**A real, pre-existing gap discovered during this review, not introduced by this slice**: `ScanJobExecutor`'s production wiring to `PostgresCallbackRegistrationRepository` is broken: `callback_repository.policy` and the registration's expected `.url` field do not exist on that class, so any production scan requesting `active.ssrf.callback` currently fails with an `AttributeError` (caught by the worker's blanket exception handler, surfacing as a generic job failure, not a worker crash). Confirmed via direct source reading and a live call against a real Postgres instance (`hasattr(repo, "policy")` → `False`). This predates Slice 18 (`postgres_callback_service.py`'s own docstring already names the gap as "explicitly future work") and was never caught because no test before this slice exercised SSRF detection through the real production component-assembly path. **Not fixed this slice**: a correct fix needs a genuinely new, cross-process poll-based `wait_for_observation()` design (the callback receiver is now, per this slice's own requirement 15, a separate OS process from the worker, so an in-process broker cannot bridge them), which is real application design work the brief's "do not redesign the WebGuard application" instruction argues against attempting inline here. Flagged as a dedicated follow-up task (background task `task_60b526a4`) with full technical detail rather than fixed narrowly or left silently undocumented.

## 16-17. Terraform validation and security review (requirements 16-17)

Terraform 1.16.0 installed (`brew install hashicorp/tap/terraform`, since Homebrew core dropped Terraform for licensing reasons). `terraform fmt -check`, `terraform init -backend=false`, and `terraform validate` all run clean across every `.tf` file in `infra/terraform/` (new: `cloudflare.tf`, `cloudhsm.tf`, `iam.tf`; modified: `networking.tf`, `postgres.tf`, `storage.tf`, `outputs.tf`, `variables.tf`, `versions.tf`).

**Security review**: Trivy 0.74.0 (tfsec's successor: tfsec is archived upstream in favor of Trivy's own `config` scanner) run against the full `infra/terraform/` directory at every severity level. Three real findings, all fixed, not waived:

- **CRITICAL** (AWS-0104): `postgres_egress_all`'s unrestricted `0.0.0.0/0` security-group egress rule removed entirely. RDS's own patching/backup/KMS/credential-rotation traffic is handled by the control plane out-of-band, not by the instance dialing out over this security group, so a zero-egress-rule (deny-all) posture is safe, not merely accepted-as-a-trade-off.
- **MEDIUM** (AWS-0178, AWS-0176): VPC Flow Logs added (`aws_flow_log` + a dedicated KMS-encrypted CloudWatch log group + a least-privilege delivery IAM role); `iam_database_authentication_enabled = true` added to RDS (purely additive: enables IAM-token auth as a possible future emergency-access path without touching `manage_master_user_password`).
- **LOW** (AWS-0017, AWS-0133, AWS-0089, AWS-0090): the new flow-log group encrypted with its own dedicated KMS key (with the CloudWatch-Logs-service-principal key-policy grant CloudWatch encryption specifically requires); RDS Performance Insights enabled (encrypted with the existing storage key); S3 server access logging added for the artifacts bucket (a separate, versioned, lifecycle-expiring log-destination bucket with a policy-based, non-ACL log-delivery grant).

Final Trivy re-scan: **0 findings at every severity** across the entire directory. This scanner is now a permanent CI gate (below), not a one-time local check.

**IAM (requirement 18)**: `iam.tf` splits the single undifferentiated artifact-storage policy `storage.tf` used to define into `api_service_access` (read-only S3, `kms:Decrypt` only) and `worker_service_access` (write-only S3, `kms:GenerateDataKey` only): the API and worker call different `ObjectStorageArtifactStore` methods (verified by reading the exact call sites: `service.py`'s `get_reference()` vs. `executor.py`'s `put()`), so granting both the same read+write policy would hand each process a permission it has no legitimate reason to hold. Both policies conditionally include narrowly-scoped `kms:Sign`/`kms:GetPublicKey` on the TrustScan signing key only when `signing_provider = "kms"` (a Terraform variable mirroring the application's own config), never `kms:*`, never CloudHSM administration. The callback-service role gets **no** IAM policy at all, deliberately: it only ever talks to Postgres (network/credential-authenticated, not IAM), so a policy with zero legitimate statements would be a resource that shouldn't exist, not an oversight. The signing-service role likewise gets no KMS/CloudHSM IAM policy in the CloudHSM path: CloudHSM's data-plane key-use boundary is HSM-native Crypto User authentication and the `cloudhsm.tf` security-group rule, neither of which IAM can narrow further.

`cloudhsm.tf` (new): `aws_cloudhsm_v2_cluster` + `aws_cloudhsm_v2_hsm`, with a security-group rule permitting CloudHSM client traffic only from the signing service's own security group (never the API's or worker's). The cluster-activation ceremony (CSR signing, crypto-officer/crypto-user setup) is documented precisely as a manual, out-of-band step with no Terraform resource, a genuine, well-known AWS CloudHSM limitation, not a gap in this configuration.

**CI (durable, not one-time)**: a new `terraform` job in `.github/workflows/ci.yml` runs `fmt -check`/`init -backend=false`/`validate`/Trivy on every push and PR, using `hashicorp/setup-terraform` (SHA-pinned, verified via `gh api`) and a SHA-256-verified Trivy release tarball (matching ADR 0028's own "SHA-256-verified downloaded artifact" pattern rather than adding a third-party scanning Action to the trusted-Action allowlist for one step).

## 20. Vitest execution (requirement 20)

**Root cause found, not merely worked around.** A stale/corrupted `node_modules/.vite`/`node_modules/.vite-temp` Vite dependency-optimization cache (left behind by an interrupted prior run) made every Vitest worker (fork or thread pool) hang indefinitely at startup, never sending the `{type: "started"}` IPC handshake the parent process waits for. Ruled out during diagnosis: Node version incompatibility, jsdom, the rolldown bundler, environment variables, and basic child-process/IPC mechanics (each independently verified working). Fix: `rm -rf node_modules/.vite node_modules/.vite-temp` before every test run, implemented as a `pretest` npm script (`apps/web/package.json`), so it is automatic and deterministic regardless of local machine state, not a manual step someone has to remember. Confirmed fixed: cold run 81s, warm run 1.06-1.18s, 39/39 tests passing, repeated multiple times across this slice's work without recurrence.

**Also discovered and closed this slice**: no frontend CI job existed at all before this slice (`npm run build`/`lint`/`test` had never run in CI). Two new jobs added: `frontend` (build/lint/test, no dependencies, runs in parallel with the backend jobs) and `frontend-e2e` (Playwright, gated on `unit-tests`/`security-gates`/`frontend`, against a real isolated Postgres). This directly makes requirement 20's "deterministic CI-safe invocation" durably enforced, not just verified once locally.

## 26. Known limitations carried forward

- **CloudHSM and Cloudflare are implemented in code/IaC but not deployed anywhere**: no cluster, no account, no zone, no PKCS#11 hardware validation. This is the slice's own explicit instruction (requirement 24), not an oversight.
- **The production SSRF callback path is currently broken** (§14-15): a real, pre-existing, now-precisely-documented gap, flagged as dedicated follow-up work rather than fixed inline.
- **The PKCS#11 `EC_POINT` encoding assumption** in `build_cloudhsm_signing_provider_from_env()` is an informed guess with both branches handled, explicitly flagged as unverified against real hardware.
- **No serving layer exists for the built SPA**: no `_headers` file, nginx config, or CSP `<meta>` tag; `PUBLIC_EDGE_SECURITY.md` §7 specifies the CSP such a layer must emit, evidenced against the real build, but does not implement the layer itself (no compute is provisioned anywhere in this repository's Terraform, consistently, since Slice 12).
- **Row-level security and full high-availability scheduler leader election remain exactly as prior slices left them**, untouched by this slice, not revisited.
- **Cross-instance rate limiting is narrowed, not fully solved**: Cloudflare's edge rules give a real shared outer bound; the application's own limiter remains per-instance for its finer-grained, per-account decisions.
