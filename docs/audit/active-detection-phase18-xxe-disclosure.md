# Active Detection, Slice 21: In-band XXE File Disclosure (CWE-611)

## Status

Complete for this detector's own initial scope, matching this project's own precedent for a detector's first build slice: an eighth active detector (in-band XXE, confirmed by reading the disclosed file's own content out of the response body) is implemented, registered directly into `ACTIVE_DETECTOR_REGISTRY`, permit-gated, and unit-tested (mocked connection, no real network). Real-network validation, a true end-to-end test, and live-target re-verification are honestly not yet attempted; see "Not Proven" below for why each was left for a later slice rather than silently skipped. Built at the user's continued request, quoting directly from `docs/audit/active-detection-phase13-xxe-callback.md`'s own "Next steps" line, written after Slice 20's live-target investigation found a real XXE vulnerability that detector could not reach.

## Design decision: why this is not just a copy of active.xxe.callback with the SYSTEM URI swapped

`active.xxe.callback` deliberately never reads response text, for a real reason: a hardened parser's own safe-rejection error routinely reuses the same vocabulary ("DOCTYPE", "external entity") a vulnerable parser's failure could also produce, so there is no reliable phrase to match on without risking a structural false positive. That reasoning still holds in general. What changed is the target: `file:///etc/passwd` resolves to a specific, highly improbable-by-coincidence content signature (`path_traversal_detector.py`'s own `_PASSWD_SIGNATURES`), not a generic error phrase. A hardened parser's rejection message cannot contain that signature; only a parser that actually opened and returned the file's content can. This is the same reasoning that already justifies `path_traversal_detector.py`'s own in-band, signature-based approach, applied to entity resolution instead of a raw filesystem path.

## Pre-implementation adversarial review

Before writing any code, a drafted design (candidate reuse via `select_xxe_candidates` import, request construction described as mirroring `path_traversal_detector.py` "exactly", `FindingIdentity.parameter` left unspecified) was reviewed by two independent lenses via the Workflow tool: one hunting concrete false-positive/false-negative scenarios, one reading the actual registry/executor/contracts/detector source directly to check the design's structural claims rather than trusting its prose.

Findings that changed the shipped design:

1. **The "mirrors path_traversal exactly" claim was imprecise about request construction.** Every existing generic-registry baseline/diagnostic detector (`sqli_error_detector.py`, `path_traversal_detector.py`, `command_injection_detector.py`, `ldap_injection_detector.py`) builds both requests with `mutate()`, changing one parameter while holding the template's real content type and shape constant, since attributability comes from that constancy. This detector cannot do that: both requests must replace the content type itself (FORM_URLENCODED/JSON to XML), the same constraint `active.xxe.callback`'s own single probe already has. The shipped module's docstring now says this plainly: classification mirrors path traversal; request *construction* mirrors the out-of-band XXE detector's own `MutatedRequest`-built-directly technique.
2. **Reusing `select_xxe_candidates` via a cross-module import would be unprecedented here, and creates real coupling.** `select_ssrf_candidates` and `select_xxe_candidates` already have near-identical dedupe-by-(endpoint, method)-plus-content-type logic, and each is defined independently in its own module rather than one importing the other, a deliberate parallel, not an oversight (`xxe_callback_detector.py`'s own docstring explicitly names the one piece of logic it needed beyond `select_ssrf_candidates`, implying it chose not to import it). Importing `select_xxe_candidates` here would silently couple this detector's real candidate set to a module versioned, tested, and audited for the out-of-band technique's own reasons. Fixed: `xxe_disclosure_detector.py` has its own private `_select_candidates`, applied inside `run_xxe_disclosure_detector` itself (candidates arrive as the same raw, page-wide, mixed GET/POST/JSON tuple every generic-registry detector receives; nothing upstream narrows it for this detector's own shape, unlike `active.xxe.callback`, whose dedicated executor function calls `select_xxe_candidates` before ever invoking the run function).
3. **`FindingIdentity.parameter` was left unspecified, and the natural-seeming choice would have been wrong.** Since the design says it "mirrors path traversal", the reflexive move is `parameter=parameter` (path traversal's own convention, valid there because its baseline/diagnostic pair really does isolate one parameter). That reasoning does not transfer: candidate selection dedupes to one template per (endpoint, method), discarding whichever parameter happened to survive, and the whole body is replaced regardless. `active.xxe.callback` already reasons through this identical problem and sets `parameter=None`; the shipped detector follows that precedent instead.
4. **The most significant finding, confirmed independently by reading `attack_surface.py`'s `InputLocation` enum directly:** the live Juice Shop vulnerability that motivated this detector (`POST /file-upload`, confirmed in Slice 20) is a genuine `multipart/form-data` file upload: the uploaded file's own content gets parsed, not the request body itself. `InputLocation` has exactly five members (QUERY, PATH, FORM, JSON_BODY, HEADER), no FILE or MULTIPART variant, so this scanner's attack-surface discovery never builds a `RequestTemplate` for a multipart endpoint at all, regardless of which detector or candidate-selection function is used downstream. Both XXE detectors replace an existing form/JSON request's entire body with a raw `application/xml` document; neither constructs a multipart envelope. **This detector, once built, cannot reconfirm the specific live finding that motivated it.** What it does add is real and independent of that specific example: in-band confirmation for the same candidate class `active.xxe.callback` already targets (any endpoint that accepts a form/JSON POST body and also parses `application/xml` sent to that same URL and method), checked in-band instead of out-of-band.
5. **A named, unfixed limitation on stateful endpoints.** The baseline-vs-diagnostic comparison assumes the endpoint behaves the same way across two requests within a scan. A file-upload-style endpoint gated by a one-time token, an upload quota, or duplicate-submission detection can make the diagnostic request fail, or its status change, for a reason unrelated to XXE. The `/etc/passwd` signature itself cannot appear in such an unrelated rejection, so this can only produce a false negative (INCONCLUSIVE on a genuinely vulnerable target), never a false CONFIRMED/PROBABLE. Not fixed this slice (would need a fresh token/nonce per request or quota-aware retry logic, out of scope for a fixed two-request-per-candidate budget); stated directly in the module's own docstring instead.
6. Two lower-severity, inherited-not-introduced observations from the review are also worth naming here rather than only in the review transcript: `_PASSWD_SIGNATURES` (copied unchanged from `path_traversal_detector.py`) does not recognize the empty-password-field format (`root::0:0:...`) some minimal/BusyBox-based images use, and the CONFIRMED/PROBABLE status-code-delta gate can mis-tier a finding on a noisy or load-balanced target. Neither is new to this detector; both already apply identically to `path_traversal_detector.py`.

## What was built

### Detector (`workers/scanner/src/webguard_scanner/xxe_disclosure_detector.py`)

Per-candidate methodology: exactly two bounded requests, a **baseline** (a well-formed, entity-free XML document, `<wgxxe>baseline</wgxxe>`, no DOCTYPE, resolves nothing) and a **diagnostic** (a single, non-recursive external general entity, SYSTEM `file:///etc/passwd`, referenced exactly once). Both are built as a `MutatedRequest` directly (`_build_probe`), not through `mutate()`, for the reason given above. The diagnostic response is checked for `path_traversal_detector.py`'s own `_PASSWD_SIGNATURES` and compared against the baseline exactly as that detector's `_classify` does: a signature already present in the baseline is not attributable to the probe; a new signature plus a status-code change is CONFIRMED; a new signature with no status-code change is PROBABLE.

Candidate selection (`_select_candidates`, private) narrows the page-wide, mixed candidate tuple to `RequestTemplate` items with a FORM_URLENCODED or JSON content type, deduped by (endpoint, method), a private, per-module copy of `active.xxe.callback`'s own `select_xxe_candidates`, not an import (see review finding 2 above).

### Registry and contracts catalog

`ACTIVE_DETECTOR_REGISTRY["active.xxe.disclosure"] = run_xxe_disclosure_detector`, dispatched automatically by `executor.py`'s existing generic per-page detection loop: no new executor function, no new dispatch category, unlike every other XXE-adjacent detector in this registry (`active.xxe.callback`, `active.ssrf.callback`). `webguard_contracts.KNOWN_TRUSTSCAN_ACTIVE_CHECKS` extended to an 11-tuple, purely additive, no schema version bump (the claims shape is unchanged; only the enum's allowed values grow, confirmed directly against `scan_permits.py`: a bump was only ever needed when the claims *shape* itself changed, as Slice 17's `missing_authentication_endpoints` field did). `test_active_detector_registry.py`'s sync assertions pass unmodified against the new set membership.

### Candidate discovery and transports: reused unmodified

Same `to_request_templates(allow_post=, allow_json=)` pipeline every other POST/JSON-capable detector already relies on. No new discovery code. As review finding 4 establishes, this pipeline has no representation for multipart file-upload candidates at all; that is a pre-existing, structural gap in discovery itself, not something this detector introduces or could fix by choosing a different candidate-selection rule.

## False-positive controls

Covered by `tests/unit/test_xxe_disclosure_detector.py` (mocked connection, no real network):

| Scenario | Mechanism that prevents a false positive | Verified |
|---|---|---|
| Genuine disclosure, status changes | (positive control) -> CONFIRMED | mocked |
| Genuine disclosure, status unchanged | (positive control) -> PROBABLE | mocked |
| Hardened parser rejects the document with a "DOCTYPE is disallowed" error | no `/etc/passwd` signature in the rejection text -> INCONCLUSIVE | mocked |
| Target reflects the raw, unresolved entity declaration text back verbatim | the literal payload text cannot match `_PASSWD_SIGNATURES` -> INCONCLUSIVE | mocked |
| Passwd-looking text already present in the baseline response | same signature in both -> not attributable -> INCONCLUSIVE | mocked |
| GET-only or legacy `DetectionCandidate` items in the page-wide candidate set | `_select_candidates` filters them out before any request is sent | mocked |
| Multiple templates for the same (endpoint, method) | deduped to one probe, not one per discovered parameter | mocked |
| Probe-budget exhaustion | `enforce_probe_budget` with `requests_per_candidate=2` rejects before any request is sent | mocked |

## Safety boundaries

Same-origin enforcement, probe budget, cancellation checks, and `before_request`/`after_request` hooks are inherited unmodified from `issue_templated_request`, identical to every other generic-registry active detector. Non-destructiveness: the only entity ever resolved is a single, non-recursive `file:///etc/passwd` read: no parameter entity, no entity-referencing-entity chain, so there is nothing resembling a "billion laughs" expansion for even a maximally naive parser, and `/etc/passwd` is read-only, small, and bounded on every realistic target, the identical safety profile `path_traversal_detector.py` already established for the same file. Evidence sanitization: the finding's provenance string never contains the raw matched signature text (`test_finding_evidence_never_contains_raw_signature_text`), and never contains authentication material (`test_evidence_never_contains_authentication_material`). `FindingIdentity.parameter` is always `None` (review finding 3), tested directly. Fingerprint determinism: `test_finding_fingerprint_determinism.py::XxeDisclosureFingerprintDeterminismTests` proves the fingerprint is stable across two runs against the same candidate and differs for a different endpoint.

Cross-detector authorization independence has not been re-proven with a dedicated test for this specific detector, the same open gap every prior generic-registry detector's own audit doc already records, relying on the shared, already-tested `active_checks` claim-matching mechanism.

## v1 scope

- `/etc/passwd` only, one entity reference, no Windows target, no alternate protocol wrapper (`php://filter`, `expect://`, `data://`), no parameter-entity-based blind exfiltration, the same exclusions `active.xxe.callback` already states, for the same reasons.
- No multipart file-upload payload delivery (review finding 4): this detector cannot construct a `multipart/form-data` request at all, and this scanner's discovery cannot represent a multipart candidate in the first place. A genuine multipart-upload XXE detector would need new discovery (a FILE/MULTIPART `InputLocation`) and a new payload mechanic (a crafted multipart envelope); neither exists yet, and building them is new scope, not attempted here.
- No retry or fresh-token handling for stateful, token/quota-gated endpoints (review finding 5): a false negative on such an endpoint is a named, accepted limitation, not a silent one.
- Real-network validation, a true end-to-end test, and live-target re-verification are not attempted this slice (see "Not Proven" below), matching this project's own precedent that a detector's first build slice ships without them.

## Implemented / Tested / Proven / Not Proven / Remaining Risks

**Implemented:** in-band XXE disclosure detector (CWE-611), independently permit-gated (`active.xxe.disclosure`), registered directly into `ACTIVE_DETECTOR_REGISTRY`, candidate-discovery-integrated, evidence-sanitized.

**Tested:** classification logic including every false-positive control listed above, candidate selection (GET/legacy exclusion, endpoint+method dedupe), payload shape (baseline has no DOCTYPE/entity; diagnostic declares exactly one entity targeting `file:///etc/passwd`; both sent with an XML content-type header; the original form body is fully replaced, not merged), evidence sanitization, `FindingIdentity.parameter` always `None`, fingerprint determinism, and the same-origin/budget/cancellation/hook safety-boundary suite every other active detector already requires. All against a fake connection.

**Proven:** the classification logic correctly distinguishes genuine disclosure from a hardened parser's rejection and from raw-payload reflection, against a mocked connection; the design's own structural integration claims (generic-registry dispatch with no new executor code, no schema bump, private per-module selection/classification helpers) were independently checked against the actual registry/executor/contracts source, not assumed from the design's prose.

**Not Proven:** that this detector correctly fires against a real, genuinely vulnerable HTTP server (no real-network validation attempted this slice); that it survives the full CLI → HTTP API → worker → executor → report pipeline (no true end-to-end test attempted this slice); that it can reach any live target at all (no live-target investigation attempted this slice, since the one live vulnerability already found, Slice 20's Juice Shop finding, is structurally unreachable by this detector for the multipart reason given above, so a repeat attempt would add no new information). All three are honest, named gaps matching this project's own precedent that a detector's first build slice defers them, not silent omissions.

**Remaining risks:**
- Cannot reach genuine multipart file-upload XXE, the exact shape of the one real live XXE vulnerability this project has found (review finding 4); closing that would require new discovery capability and a new payload-delivery mechanic, out of scope here.
- False negative (INCONCLUSIVE) on a token-gated, quota-gated, or duplicate-submission-gated stateful endpoint whose diagnostic request fails or changes status for a reason unrelated to XXE (review finding 5).
- `_PASSWD_SIGNATURES` does not recognize the empty-password-field format (`root::0:0:...`) some minimal/BusyBox-based images use; inherited unchanged from `path_traversal_detector.py`.
- The CONFIRMED/PROBABLE status-code-delta gate can mis-tier a finding (under-confidence a common true positive, over-confidence unrelated status noise); inherited unchanged from `path_traversal_detector.py`, not introduced here.
- Cross-detector authorization independence for this specific detector is inferred, not independently reconfirmed.

**Next steps:** real-network validation against a purpose-built local fixture (mirroring `test_xxe_callback_detector_live.py`'s `xml.parsers.expat`/`ExternalEntityRefHandler` mechanism, this time reading the response body for the disclosed content instead of waiting for a callback), a true end-to-end test (mirroring `test_path_traversal_checks_e2e_lab.py`'s generic-registry shape, not the callback-based e2e pattern), and, if this scanner ever adds multipart/file-upload candidate discovery, a genuinely new multipart-XXE detector capable of reconfirming the specific Juice Shop finding this one cannot reach.
