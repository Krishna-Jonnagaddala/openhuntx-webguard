# P1-2 Phase H: SECURITY DEFINER boundary review (2026-09-19)

Requested review of the specific functions named at this mandate's checkpoint, after the `set_password_hash`/`get_principal` cluster fix (`docs/PROJECT_EXECUTION_LEDGER.md`'s 2026-09-18 entry) and the earlier Phase F/H design rounds. This document answers, for each named function: who can call it, what trust boundary or narrow cross-tenant capability the design actually relies on, what untrusted input it accepts, what data or mutation it exposes, and how a bad caller or a bad identifier is rejected. It also answers the two explicit standing questions this mandate raised: whether `api_tenant_data` can obtain an arbitrary principal's password hash through `resolve_password_hash`, and what `callback_receiver`'s effective privileges actually are, proven rather than asserted.

Working principle, stated once here rather than repeated per function: **a primary-key match is a lookup condition, not automatically an authorization boundary, and a hardened `search_path` does not prove tenant isolation.** Every function below is judged against that standard, not against "it filters by ID" alone.

All SQL quoted here is from `infra/postgres/bootstrap/tenant_isolation_control_functions.sql` at this branch's current head (commit `c6a9088`). Every claim about "the only caller(s)" was re-verified by grepping the actual Python source at the same commit, not carried over from an earlier design round.

## resolve_password_hash

```sql
CREATE OR REPLACE FUNCTION webguard_control.resolve_password_hash(p_principal_id uuid) RETURNS text
    LANGUAGE sql STABLE SECURITY DEFINER SET search_path = pg_catalog, pg_temp
    AS $$ SELECT password_hash FROM public.password_credentials WHERE principal_id = p_principal_id; $$;
```

- **Owner**: `identity_function_owner`. **Grantee**: `api_tenant_data` only (`REVOKE ALL ... FROM PUBLIC` immediately above the grant).
- **Untrusted input**: `p_principal_id`, a bare UUID, no organization scoping of any kind in the function body.
- **Data exposed**: one principal's `password_hash` (an Argon2id hash, never a plaintext secret) or NULL if no `password_credentials` row exists for that ID.
- **Rejection mechanism**: none, structurally. A syntactically valid but nonexistent `principal_id` returns NULL (proven by `test_postgres_control_functions.py`'s `test_resolve_password_hash_matches_current_lookup_shape`); a real `principal_id` belonging to a **different** organization than the caller's own returns that principal's real hash, with nothing in this function to stop it (proven directly by the new `test_resolve_password_hash_has_no_tenant_filter_by_design`, added by this review: two organizations, two principals, and a straight cross-tenant SQL call to this function returns the second organization's hash unmodified). **This is not a bug in the function; it is the same shape Phase F already established for `resolve_api_token`/`resolve_browser_session` (secret material returned by ID, no tenant filter), and changing it now would be inconsistent with an already-reviewed, unrelated-to-this-pass precedent, not a narrower fix.**
- **Answering the explicit question (can `api_tenant_data` obtain an arbitrary principal's hash through this function)**: at the database-grant level, yes, mechanically: any code running as `api_tenant_data` that calls this function with any `principal_id` value gets that principal's hash back, full stop. Postgres's GRANT model has no way to restrict *which* argument values a granted role may pass. The boundary this design actually relies on is therefore **entirely at the Python call-site layer**, not the database layer, and was verified exhaustively, not assumed: `resolve_password_hash` is called from exactly one place, `PostgresIdentityRepository.get_password_hash` (`postgres_identity.py`), which is itself called from exactly two places in the entire codebase (verified by `grep -rn "get_password_hash" apps/api/src/webguard_api/*.py`, re-run for this review):
  1. `service.py`'s `login`: `principal = self.identity.get_principal_by_email(email)` (the server resolves `principal_id` itself, from the request's `email` field, by looking up whichever account actually owns that email; this is exactly the identity the caller is trying to authenticate *as*, not a foreign one), then `get_password_hash(principal.principal_id)`.
  2. `service.py`'s `change_password`: `get_password_hash(context.principal_id)`, where `context` is the already-authenticated session's own `AuthContext`, never a value read from the request body.
  Neither call site ever passes a request-body-supplied or otherwise attacker-chosen `principal_id`. This was proven, not merely read, by the same technique used for the `set_password_hash` fix: `test_postgres_password_hash_tenant_context.py`'s `test_change_password_ignores_a_different_principal_id_in_the_request_body` injects a foreign `principal_id` into an authenticated `change_password` call's own JSON body and confirms it has zero effect (only `context.principal_id`'s own password is ever touched), and the full login/registration/reset flows in that same file exercise `get_password_hash` exclusively through its two real, safe call sites under real forced RLS.
  **Verdict**: this is an intentional, already-established authentication capability (a two-phase "resolve minimal secret material, verify in Python" pattern used identically for API tokens and browser sessions), not a newly introduced or newly discovered hole, and every currently-reachable path into it is safe by construction of the Python call sites, not by a database-level restriction. **This is a narrower guarantee than a database-enforced boundary would be**: it depends on no future code ever adding a third call site that passes an untrusted `principal_id`. That dependency is now written down explicitly (this document, plus a permanent regression test), where before it was implicit. If a future change needs a stronger, database-enforced guarantee here, the correct fix is the same one already applied to `set_password_hash`: thread `organization_id` through and filter by it, or add a paired `resolve_principal_organization`-style pre-check; that fix was not applied here because it would be pure defensive hardening against a call site that does not exist today, not a fix for a demonstrated defect, and is out of scope for this pass on that basis.

## resolve_identity_token

```sql
CREATE FUNCTION webguard_control.resolve_identity_token(p_token_id uuid) RETURNS TABLE (
    token_id uuid, principal_id uuid, organization_id uuid, purpose text,
    secret_hash text, expires_at timestamptz, used_at timestamptz, created_at timestamptz
) LANGUAGE sql STABLE SECURITY DEFINER SET search_path = pg_catalog, pg_temp
    AS $$ SELECT ... FROM public.identity_tokens AS t WHERE t.token_id = p_token_id; $$;
```

- **Owner**: `identity_function_owner`. **Grantee**: `api_tenant_data` only.
- **Untrusted input**: `p_token_id`, a UUID, but this is the row's own primary key, not the actual bearer secret. The real secret is a separate, high-entropy value (`secrets.token_urlsafe`-shaped, per this codebase's identity-token issuance convention) whose SHA-256/scrypt hash is stored in `secret_hash`; verification happens in Python via `_verify_secret`, never in SQL. Knowing a `token_id` alone (e.g. if it ever leaked into a log) is not sufficient to pass verification.
- **Data exposed**: the full identity-token row, including `secret_hash`, for the given `token_id`, again with no tenant filter.
- **Only caller**: `PostgresIdentityRepository.consume_identity_token`, itself called only from `service.py`'s `confirm_password_reset`/`confirm_email_verification`/`accept_invitation`, each of which extracts `token_id` from the caller-supplied token string's own prefix format (`_parse_prefixed_secret`), then immediately verifies the accompanying secret against `secret_hash` (`row[4]`) before trusting anything else in the row, then checks `purpose`/`used_at`/`expires_at` (rows 3/6/5) before proceeding. `organization_id` (row 2) is used only *after* successful secret verification, to call `set_tenant_context` for the subsequent, now-legitimately-scoped write. This is the same two-phase pre-auth-resolver pattern as `resolve_api_token`/`resolve_browser_session`, and identically safe for the identical reason: the thing an attacker would need to forge to make this function return something useful (`token_id` alone, without the matching secret) does not let them pass the secret-hash check that gates every subsequent action.
- **Rejection mechanism**: an unknown `token_id` returns zero rows (proven, `test_resolve_identity_token_matches_current_lookup_shape`), which `consume_identity_token` turns into `identity_token_invalid` before any other field is read.
- **Schema-widening review**: the 2026-09-17 DROP/CREATE that appended `created_at` as an 8th column is covered separately below (schema-compatibility section) and does not change this function's authorization shape at all; it changes only what is returned once authorization already passed.

## Worker job/permit resolvers: `resolve_job_permit_binding`, `resolve_job_cancellation_requested`, `resolve_job_scope`

All three share one trust model, stated once:

```sql
-- resolve_job_scope
SELECT organization_id, submitted_by FROM public.scan_jobs WHERE job_id = p_job_id;
-- resolve_job_cancellation_requested
SELECT cancellation_requested FROM public.scan_jobs WHERE job_id = p_job_id;
-- resolve_job_permit_binding
SELECT permit_id, permit_sha256 FROM public.job_permits WHERE job_id = p_job_id;
```

- **Owner**: `worker_function_owner`. **Grantee**: `worker_tenant_data` only.
- **Untrusted input**: `p_job_id`, a bare UUID, no tenant filter in any of the three.
- **Trust boundary, stated explicitly rather than assumed**: `worker_tenant_data` is not a tenant-scoped role in the same sense `api_tenant_data` is under `tenant_connection`; it is the identity a worker process runs as while executing a job it already holds a lease on. The actual authorization event already happened earlier, in `claim_next_job`'s own `FOR UPDATE ... SKIP LOCKED` claim (cross-tenant by design: a worker pool serves every organization's jobs from one shared queue), which is the only way a worker legitimately learns a `job_id` at all. These three resolvers exist because that already-legitimately-held `job_id` is the worker's *only* credential for the rest of a job's lifecycle (there is no per-organization worker fleet, and worker processes are never given a customer-facing identity to authenticate against). A `job_id` is a UUIDv4 (128 bits of entropy, unguessable by brute force) and is never exposed to any other tenant's caller through any API response this codebase has (jobs are read back only by the organization that owns them, via `api_tenant_data`'s own tenant-scoped queries elsewhere). So the practical boundary is: *possession of a job_id, which only ever reaches a worker through its own legitimate claim, or through internal job-to-job references the worker already legitimately holds.*
- **Data exposed**: `resolve_job_scope` returns `organization_id`/`submitted_by` only (not the full job row); `resolve_job_cancellation_requested` returns one boolean; `resolve_job_permit_binding` returns `permit_id`/`permit_sha256` only. Each is deliberately narrower than a full-row read (output minimization, matching this codebase's own stated Section 13 principle), and none of the three can be used to enumerate or browse jobs (each takes exactly one `job_id`, returns nothing on a miss, and provides no ordering/pagination primitive).
- **Rejection mechanism**: an unknown `job_id` returns NULL/zero rows in all three; `resolve_job_cancellation_requested`'s own docstring notes `scan_jobs.cancellation_requested` is itself `NOT NULL` (migration 0004), so a NULL return is exactly how "not found" is distinguished from "found, not cancelled," and the calling Python code (`is_cancellation_requested`) raises `job_not_found` on that NULL, never on a false-but-present value.
- **Verdict**: consistent with the file's own precedent (`resolve_job_organization`, already reviewed and unchanged this pass) and with the worker/scheduler architecture's actual authorization model (lease-holding, not per-tenant identity). Not a gap; the primary-key-only shape here is correct *given* the caller already holds the ID through a real claim, which is a materially different situation from `resolve_password_hash`, where the "caller already legitimately holds this ID" property has to be proven from the Python call graph rather than from an entropy/possession argument, and was (see above).

## Scheduler resolvers: `resolve_schedule_permit_binding`, `resolve_schedule_request_shape`, plus `enqueue_due_schedule`

```sql
-- resolve_schedule_permit_binding
SELECT permit_id, permit_sha256 FROM public.schedule_permits WHERE schedule_id = p_schedule_id;
-- resolve_schedule_request_shape
SELECT target, authorization_id, mode FROM public.scan_schedules WHERE schedule_id = p_schedule_id;
```

- **Owner**: `scheduler_function_owner`. **Grantee**: `scheduler_tenant_data` only.
- **Trust boundary**: identical shape and identical reasoning to the worker resolvers above, with `schedule_id` (also a UUIDv4) playing the role `job_id` does there. The scheduler process is the one component that discovers due schedules cross-tenant by design (`list_due_schedules`'s own `state = 'active' AND next_run_at <= p_now` predicate has no organization filter, matching its job of finding every organization's due work), so every schedule ID the scheduler ever handles came from that same legitimate, already-cross-tenant discovery step, never from an external caller.
- **`resolve_schedule_request_shape`'s specific purpose**: supplies `target`/`authorization_id`/`mode`, immutable for a schedule's lifetime, so `postgres_schedules.py`'s Python caller can compute `ScanJobRequest.fingerprint` (a canonical-JSON SHA-256 this codebase deliberately keeps as a single, non-duplicated Python algorithm, per this file's own comment) *before* calling `enqueue_due_schedule`, which needs that fingerprint as an explicit parameter rather than recomputing it in PL/pgSQL.
- **`enqueue_due_schedule`** (the function actually mutating state): re-derives its own authorization independently of anything the caller supplies for the sensitive checks, rather than trusting resolver output blindly:
  - Confirms the schedule is still `active`, at the exact expected `revision`, and actually due (`next_run_at <= p_now`) via its own `FOR UPDATE` read, not by trusting a value the caller precomputed.
  - Confirms the authorization is *still* assigned to the organization (`organization_authorizations` `EXISTS` check) at enqueue time, not merely at some earlier resolve time, closing a TOCTOU window a naive "resolve then enqueue" split could otherwise open.
  - Confirms the permit binding matches exactly (`permit_id`/`permit_sha256`) and that the permit itself is still valid (`revoked_at IS NULL AND not_before <= p_now AND p_now < expires_at`), independently re-checked inside this same function, not carried over from a resolver call.
  - Untrusted input here includes `p_request_fingerprint` (caller-supplied, per the design note above) and `p_authorization_sha256`/`p_permit_sha256`; none of these can substitute for the independent `organization_authorizations`/`scan_permits` existence checks above, so a caller cannot enqueue a job against a permit or authorization it does not, independently and currently, hold.
  - **Rejection mechanism**: seven distinct named outcomes (`not_due`, `authorization_not_assigned`, `binding_changed`, `permit_invalid`, `raced`, `schedule_conflict`, plus the schema-widened success case `ok`), each leaving the transaction with zero writes, mirroring the current Python method's own exception/`None`-return shape exactly (re-verified against `postgres_schedules.py`'s `enqueue_due_schedule`, not assumed carried over from the design round).
- **Verdict**: correctly designed. The two small resolvers are lease-shaped like the worker ones; the function that actually mutates state (`enqueue_due_schedule`) does not lean on resolver output for its security-relevant checks at all, it re-derives them from source tables directly inside its own transaction.

## `resolve_and_record_callback_observation`, and the `callback_receiver` LOGIN role

```sql
CREATE OR REPLACE FUNCTION webguard_control.resolve_and_record_callback_observation(
    p_token_value text, p_method text, p_source_class text, p_observed_at timestamptz
) RETURNS boolean LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE v_revoked_at timestamptz; v_expires_at timestamptz;
BEGIN
    SELECT revoked_at, expires_at INTO v_revoked_at, v_expires_at
    FROM public.callback_registrations WHERE token_value = p_token_value;
    IF NOT FOUND OR v_revoked_at IS NOT NULL OR v_expires_at <= p_observed_at THEN RETURN FALSE; END IF;
    INSERT INTO public.callback_observations (...) VALUES (gen_random_uuid(), p_token_value, p_method, p_source_class, p_observed_at);
    RETURN TRUE;
END; $$;
```

- **Owner**: `callback_function_owner` (a privileged owner role nothing is ever a member of; it exists only to own this one function, matching every other function-owner role's design). **Grantee**: `callback_receiver` only.
- **Untrusted input**: `p_token_value` is genuinely attacker-influenced, since this function's only caller is the public, unauthenticated SSRF-callback HTTP receiver (`callback_server.py`), reachable by a scanned target's own outbound request with no session, no API token, and no prior authentication of any kind. `p_method`/`p_source_class` are also caller-influenced (HTTP method, coarse classification), but neither is used in any conditional logic inside this function, only stored. `p_observed_at` is **not** attacker-controlled: it is captured once, in Python, before any persistence attempt (`callback_server.py`'s own `_record_observation_with_bounded_retry`), and passed in as a trusted value rather than the function calling `now()`/`clock_timestamp()` itself, exactly matching how `claim_next_job`/`terminal_transition` treat their own `p_now`.
- **Trust boundary**: a valid, unexpired, unrevoked `token_value` is the entire authorization for this function, by design (it is standing in for "did the target we scanned actually receive our callback," which by its nature has no other credential to check). This is why the token is generated with `secrets.token_urlsafe(32)` (`postgres_callback_service.py`'s own docstring: 256 bits from Python's CSPRNG), not a sequential or otherwise-guessable ID, and why `record_observation` is one atomic function rather than a separate "check" then "record" pair (this file's own Section 22 comment: a two-function split would reopen a TOCTOU window between validity-check and persistence that the single-transaction design already closes).
- **Data exposed/mutated**: a single boolean result, and one INSERT into `callback_observations` on success. No SELECT of any other table, no UPDATE, no information about *why* a call failed (expired vs. revoked vs. unknown token all return the same `FALSE`, deliberately: this file's own Section 23 note is that current application code already collapses these three cases into the same generic outcome, so this function does not introduce a new oracle beyond what already existed).
- **Rejection mechanism**: `NOT FOUND OR v_revoked_at IS NOT NULL OR v_expires_at <= p_observed_at` in one guard, `RETURN FALSE` with no partial write.

### `callback_receiver`'s actual effective privileges, proven not asserted

The explicit ask was to check effective privileges through PUBLIC, inherited roles, database/schema defaults, and other executable functions, and to prove the role cannot assume broader roles or read/write unrelated tables. This was done as a dedicated test (`test_postgres_phase_h_gap_closure.py`'s `test_callback_receiver_has_exactly_one_privilege_anywhere`, added this pass, passing against a real, fully-bootstrapped database), not by reading the GRANT statements alone:

- **EXECUTE**: iterated all 19 *other* `webguard_control` functions by `(oid, proname)` and asserted `has_function_privilege('callback_receiver', oid, 'EXECUTE')` is `FALSE` for every one of them. `callback_receiver` can execute exactly one function in this schema.
- **Role membership**: asserted `pg_has_role('callback_receiver', <role>, 'MEMBER')` is `FALSE` for all seven other bootstrap roles (the three tenant-data roles and the four function-owner roles), and separately asserted zero rows in `pg_auth_members` where `member = callback_receiver`'s OID, covering both the "is a member of" and "granted membership to others" directions. `callback_receiver` cannot `SET ROLE` to, or be granted into, anything.
- **Table grants**: asserted zero rows in `information_schema.role_table_grants` for this role, and separately swept `aclexplode(pg_class.relacl)` across every table in `public`, asserting zero matches, a second, structurally independent representation of the same fact (catching a grant that one query shape might miss but the other would not).
- **Schema usage**: `has_schema_privilege('callback_receiver', 'webguard_control', 'USAGE')` is confirmed **`TRUE`**, and this is correct, not a leak: `tenant_isolation_control_functions.sql`'s own header states EXECUTE on a function requires USAGE on its schema too, and this grant is the explicit, reviewed prerequisite for the one EXECUTE this role legitimately holds. (An earlier draft of this same test incorrectly asserted this should be `FALSE`; corrected before running, by cross-checking against the SQL file's own comment rather than an assumption about what "narrow" should mean here.) `public` schema USAGE was deliberately *not* asserted against, since PostgreSQL grants PUBLIC (and therefore every role, including this one) default USAGE on schema `public`, unrevoked for any role anywhere in this project; asserting against it would be testing a repo-wide default unrelated to `callback_receiver`'s own design, not a real boundary.
- **LOGIN and network-reachability boundary**: `callback_receiver` is the sole `LOGIN` role among the eight bootstrap roles (the other seven are `NOLOGIN`, reached only via `SET LOCAL ROLE` from the ambient `webguard` identity). This means the callback-service process authenticates to Postgres directly and separately, with its own dedicated DSN/credential (`WEBGUARD_CALLBACK_DATABASE_URL`, confirmed against `cli.py`'s `_callback_service_command`, which explicitly refuses to start without it and explicitly does not fall back to `WEBGUARD_DATABASE_URL`), never inheriting the "webguard" ambient role's own broader privileges the way a bug in the api-serve/worker/scheduler processes theoretically could (those three all still connect as "webguard" first, then narrow via `SET LOCAL ROLE`; a wiring bug there degrades, at worst, to the full "webguard" identity, whereas an equivalent bug in the callback-service process has no "webguard" identity to fall back to at the TCP-authentication layer at all).

**Verdict**: `callback_receiver` is proven, not merely designed, to be able to do exactly one thing: call `resolve_and_record_callback_observation`, whose only side effect is one `INSERT` into `callback_observations`, gated by a 256-bit unguessable token it did not choose and a trusted, non-forgeable timestamp. No path to any other function, any other role, or any other table was found under adversarial-shaped testing (both the ACL-catalog query and the raw `aclexplode` sweep), and the LOGIN/dedicated-DSN design means even a connection-handling bug in this specific process cannot silently inherit broader ambient privilege the way an equivalent bug could in the three `SET LOCAL ROLE`-based processes.

## Summary table

| Function | Owner | Grantee | Tenant-filtered? | Real boundary |
|---|---|---|---|---|
| `resolve_password_hash` | `identity_function_owner` | `api_tenant_data` | No | Python call-site discipline (2 verified callers, neither attacker-influenced) |

| `resolve_job_scope` / `resolve_job_cancellation_requested` / `resolve_job_permit_binding` | `worker_function_owner` | `worker_tenant_data` | No | `job_id` possession, itself gated by `claim_next_job`'s real lease claim |
| `resolve_schedule_permit_binding` / `resolve_schedule_request_shape` | `scheduler_function_owner` | `scheduler_tenant_data` | No | `schedule_id` possession, itself gated by `list_due_schedules`'s real discovery step |

No new code changes resulted from this specific review beyond the two new proof tests already committed (`test_resolve_password_hash_has_no_tenant_filter_by_design`, `test_resolve_principal_organization_matches_current_lookup_shape`, both in `test_postgres_control_functions.py`) and the pre-existing `test_callback_receiver_has_exactly_one_privilege_anywhere`. Every function reviewed here was found to already match its own documented design intent; the value of this pass was proving that match empirically, and writing down the actual trust boundary (possession-of-an-unguessable-ID, or Python call-site discipline, rather than a database-enforced tenant filter) explicitly, in the exact cases where that boundary is real but easy to mistake for something stronger than it is.
