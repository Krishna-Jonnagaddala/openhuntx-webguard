# SSRF Callback Service Deployment (Slice 18)

## Status

**Isolation and abuse-control infrastructure implemented; DNS/edge model prepared; the actual production SSRF-detection data path is broken independently of this slice's work.** §5 states the last point precisely — it is a real, currently-existing gap this slice discovered while reviewing the callback path for public exposure, not something Slice 18 introduced, and not something Slice 18 fixes. `docs/production/INFRASTRUCTURE_REQUIREMENTS.md`'s "What NOT to build first" already named the discipline this document follows: *"Do not build a public callback service before deciding the DNS/TLS/abuse-control model; the interface is ready, the endpoint is not."* This slice decides that model; it does not turn the receiver into a general public relay.

## 1. What already existed (Slice 10/12), unchanged by this slice

`CallbackHttpReceiver` (`apps/api/src/webguard_api/callback_server.py`) is a real, independently-startable `ThreadingHTTPServer` — not a mock — accepting `/<scan_id>/<token>` and recording the observation via an injected sink. Correlation is **token-only**: never the source address, never the `Host` header a request arrives with. This is what makes moving it behind a real public DNS name safe without weakening the security property — even a rebound DNS name or a spoofed `Host` header is only ever evidence for the exact token it carries, nothing else. Every request, accepted or rejected, gets an identical generic response (`204` by default) — the receiver never reflects, redirects, or executes anything from the request.

`PostgresCallbackRegistrationRepository` (Slice 12) already gives token registration and observation *metadata* — `callback_registrations` (token, `organization_id`, `scan_id`, `job_id`, `permit_id`, `target`, `authorization_id`, `expires_at`) — durable, tenant-isolated storage satisfying requirement 14's "preserve... tenant/scan binding, bounded observation storage" at the schema level.

## 2. What this slice adds: rate limiting (requirement 15)

A public callback endpoint is itself an abuse target — unbounded inbound requests would grow the `callback_registrations`/observations table without bound. `CallbackHttpReceiver` gained an optional `rate_limiter: FixedWindowRateLimiter | None` (the same limiter class the main API already uses, reused rather than a second implementation). A rate-limited request is **not recorded**, but receives the *identical* generic response every other request gets — an external observer cannot distinguish "throttled" from "recorded" from the wire response alone, preserving the "never give an oracle" posture the receiver has always had. `tests/unit/test_callback_service.py::CallbackReceiverRateLimitTests` proves both the throttling and the response-indistinguishability directly.

This is scoped to protecting the receiver's *own* correlation-store writes. The receiver has been its own separate process/thread pool since Slice 10 — unbounded callback traffic could never consume the main API/worker's own capacity even before this slice; the rate limit is a new, independent bound on a resource (the database) the receiver itself could otherwise exhaust.

## 3. Independent deployability (requirement 15)

`webguard-api callback-service` (new subcommand, `cli.py`) runs `CallbackHttpReceiver` as its own standalone process, backed by `PostgresCallbackRegistrationRepository` and reading `WEBGUARD_DATABASE_URL` plus callback host/port/rate-limit environment variables — entirely independent of `webguard-api serve`/`worker`. This satisfies "the callback endpoint should be independently deployable/scalable from the main API" directly: it can be deployed as its own service, scaled to its own replica count, and rate-limited to its own bound, all without touching the API/worker's own capacity or deployment cadence.

## 4. DNS and edge model (requirement 14)

`infra/terraform/cloudflare.tf` provisions `callback.openhuntx.com` as its own proxied `cloudflare_dns_record`, pointing at `var.origin_callback_hostname` — a **distinct origin from `api.openhuntx.com`**, not a path under the same one, reflecting §3's independent-deployability property in the DNS layer itself. It receives the same edge WAF/TLS treatment as the other two hostnames (`docs/production/PUBLIC_EDGE_SECURITY.md`), plus its own edge rate-limit consideration is deliberately *not* added in this slice — the receiver's own per-IP limiter (§2) is the reviewed control for this endpoint; requirement 8's "do not enable aggressive rules that break WebGuard workflows" argues against stacking a second, independently-tuned edge limit on top of a purpose-built application one without a concrete reason to.

This is preparation, not activation: no DNS name here has been verified to exist, no Cloudflare zone has been created (requirement 24). "Prepare `callback.openhuntx.com`" is satisfied at the IaC/design level; nothing here turns the receiver into an uncontrolled public relay — every existing safety property (token-only correlation, generic uniform responses, bounded observation storage, now bounded request rate) is preserved exactly, not loosened, by exposing it publicly.

## 5. A real, pre-existing gap this slice discovered: production SSRF detection is currently non-functional

While reviewing the callback path for public exposure, direct code inspection (confirmed against a real PostgreSQL instance, not just static reading) surfaced that **`ScanJobExecutor`'s production wiring cannot actually complete a live SSRF-callback detection today.**

`production_startup.py` constructs `callback_repository = PostgresCallbackRegistrationRepository(pool)` and passes it directly as `ScanJobExecutor`'s `callback_repository`. But the executor's `_apply_ssrf_callback_detection()` calls `callback_repository.policy` and expects `register()` to return a `.url`-bearing token (`ssrf_callback_detector.py` does `token.url` immediately after registering) — `PostgresCallbackRegistrationRepository` has no `.policy` attribute and its `register()` returns a `ScopedCallbackRegistration` dataclass with no `url` field at all. The first attribute access raises `AttributeError`. `ScanJobWorker.run_once()`'s blanket exception handler catches it and marks the job `FAILED` rather than crashing the worker process, so the practical, currently-existing symptom is: **any production-mode scan whose permit includes `active.ssrf.callback` fails with a generic internal error instead of running the check.**

This predates Slice 18 — `postgres_callback_service.py`'s own module docstring, written when that class was first added, already names it: *"Wiring this repository in as the executor's live callback broker... is explicitly future work."* It was never caught because no test before this slice exercised SSRF detection through the real production component-assembly path (every existing SSRF E2E test uses the local/lab `CallbackRepository`/`InMemoryCallbackBroker` path directly, which works correctly).

**Why this slice does not fix it**: a correct fix needs new design, not a quick patch — because Slice 18 made the callback receiver an independently-deployable *separate process* (§3), the worker process's registration and the receiver process's observation now happen in two different OS processes communicating only through PostgreSQL. `InMemoryCallbackBroker`'s current wait mechanism is in-process (built for one process to register and observe); a correct fix needs a poll-based, cross-process `wait_for_observation()` on the Postgres-backed path, a `.url`-constructing adapter (using the already-validated-but-never-consumed `WEBGUARD_CALLBACK_SERVICE_HOSTNAME` config field — also discovered, during this same review, to be validated at startup but never actually read anywhere else in the codebase), and a `.policy` source — each a real design decision (poll interval, timeout-budget interaction, stale-registration cleanup), not a one-line wire-up. Building that now would be exactly the kind of applica­tion redesign this slice's own brief instructs against. It has been flagged as a dedicated follow-up task with the full technical detail above (task `task_60b526a4`), rather than fixed narrowly or left undocumented.

**What this means for requirement 14's "prepare for the existing SSRF detector"**: preparation (DNS, isolation, rate limiting, token/entropy/expiry properties) is complete and reviewed; the detector it is preparing for does not currently produce a finding through the production runtime path. Requirement 24's "not proven" framing for CloudHSM/Cloudflare applies here in a different, more direct sense — this specific detector's production path is not just unprovisioned, it is provably broken today, independent of anything this slice built.
