# WebGuard-only release checklist

Product decision (2026-09-22): ship OpenHuntX's first release with WebGuard as the
available product. SOC and Compliance continue as separate development tracks and are
not release blockers for WebGuard; see "Deferred, not blocking" and
`docs/production/WEBGUARD_RELEASE_CHECKLIST.md`'s own SOC/Compliance rows below for
what keeps them out of the critical path without pretending they do not exist in the
codebase.

This is the one finite checklist for that release. It supersedes no other document's
own evidence: `docs/RELEASE_READINESS.md` still holds the six-gate verdict framework
and `docs/PROJECT_EXECUTION_LEDGER.md` still holds the full P1-N mandate history. This
file exists because neither is structured as a closeable list with an acceptance
criterion and a remaining dependency per row, which a release decision needs and an
open-ended narrative does not give.

Status values used below: **DONE** (evidence exists, acceptance criterion met),
**PARTIAL** (some of the requirement is met; the gap is named), **OPEN** (not met),
**OWNER DECISION** (the code/evidence exists on both sides of a choice; a person, not
more engineering, closes this row).

## Newly found during this checklist's own verification, not yet fixed

- **Correction to a prior entry in this section.** A previous pass here flagged a freshly-registered organization through `webguard-api serve --environment lab` ending up with zero module-entitlement rows as an apparent bug and spawned a follow-up task for it. Direct reproduction this session showed it is not one: `register_account` correctly grants entitlements in-process; the symptom only appears after a `serve` process restart, because `InMemoryModuleEntitlementRepository` (lab/dev's deliberate, documented in-memory backend) does not persist across restarts, exactly matching how `scan_repository`/`finding_repository`/`coverage_repository` already behave in `_components()`. The stale follow-up task was withdrawn.
- `create_organization`'s exception handling normalizes every `IntegrityError` (unique violation, not-null violation, or otherwise) into the same generic `organization_conflict` message. Found while rehearsing the M25 rollback procedure: old application code run against a schema that has drifted ahead of it (a non-backward-compatible migration already applied) fails with this same generic conflict error, which would mislead an operator toward "duplicate name" during a real incident instead of "the schema and the code have drifted." Documented plainly in `docs/production/DEPLOYMENT_ROLLBACK.md`; not fixed here, since distinguishing the integrity-violation cases is a separate, small, independently-scoped code change.
- `SocPage.tsx`/`ComplianceAssertionsPage.tsx` default the deployment-wide `available` flag to `true` when `GET /v1/module-entitlements` returns zero rows for that organization, a case `service.py`'s `list_module_entitlements` docstring itself calls legitimate ("an organization created before this route existed... may legitimately have zero rows"). Found while validating the integrated candidate (merging PR #70 into PR #75 locally surfaced this in `SocPage.tsx`'s conflict, but the bug itself predates and is independent of that merge): the underlying API route still enforces the restriction correctly regardless (confirmed live: `GET /v1/soc/connectors` still returns 404 `module_not_available_in_this_deployment` in this exact state), so this is a UI defect, not a security bypass, but the page shows the wrong message and fires a request that always fails. Not fixed here; flagged as its own follow-up task (`task_c0639448`).

## How to use this checklist

Every mandatory row needs to reach DONE, or an explicit OWNER DECISION needs to be recorded against it, before this release's go/no-go is called. "Deferred, not blocking" rows are not silently dropped: each one names the tracking document that still owns it. This file should be updated in place (not superseded by a new file) as rows close; each closure should cite the commit/PR that closed it, matching the discipline `docs/PROJECT_EXECUTION_LEDGER.md` already uses.
