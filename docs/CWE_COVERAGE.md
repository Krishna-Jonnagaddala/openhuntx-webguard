# OpenHuntX WebGuard CWE Coverage

## Status language

This registry follows the same discipline as [`ROADMAP.md`](ROADMAP.md): it separates what is implemented and tested today from what is planned. It is not a claim that WebGuard detects every weakness listed, and it is not a transcription of the full CWE catalog.

## Scope discipline

WebGuard does not claim to scan for every CWE. The CWE catalog (including the reference view consulted while scoping this registry) covers roughly a thousand entries spanning memory safety, language-specific misuse, hardware, and internal software-development defects that are not observable by an external, black-box web assessment tool. Those entries are out of scope by construction and are not enumerated here as "not applicable" noise.

This registry instead tracks only CWE classes that are:

- web- or API-relevant, and
- externally observable (or detectable with explicit, authorised authenticated access) without source-code review.

Each tracked CWE has one status:

- **IMPLEMENTED**: detection logic exists in a scanner analyzer, runs as part of a normal scan, and is covered by tests.
- **IMPLEMENTED (active, permit-gated)**: detector code exists, is tested, and is reachable end-to-end through the API job/executor pipeline when a TrustScan permit explicitly authorizes it (`active_checks` claim). Not reachable through the standalone `webguard scan` CLI, which does not use TrustScan permits at all. See the linked audit doc for exactly what was and wasn't validated.
- **PARTIAL**: some indicators can be detected, but exploitability cannot always be established from the outside.
- **PLANNED**: defined as in-scope, not yet implemented.
- **NOT APPLICABLE**: cannot reasonably be tested externally, intentionally excluded.

## Slice 16: CSRF added as a passive check, not an active detector

A sixth post-freeze addition, at the user's continued request, but a different shape from every one before it: `web.html.csrf_token` for CWE-352 is a passive check added to the existing `html_analyzer.py`, not a new active detector.

The reason is structural, not a style preference. Every active detector added in Slices 12-15 (path traversal, command injection, XXE, open redirect, LDAP injection) sends a diagnostic payload deliberately engineered to be non-destructive regardless of whether the target is vulnerable: a syntax-breaking character, a callback to WebGuard's own infrastructure, a redirect the transport never follows. Confirming CSRF the same active way would require actually submitting a well-formed state-changing request without a valid token and observing whether the action completes; if the target is genuinely vulnerable, that observation IS the action completing for real. There is no payload shape that makes this non-destructive, which is exactly the "active exploitation... destructive testing... not part of the current initial release scope" line `ROADMAP.md` already states. Read directly, `attack_surface.py`'s own `_classify_safety` keyword list also does not fully block this (only endpoints matching specific keywords like "payment" or "delete" are excluded; a great many real state-changing forms aren't caught by that list and remain reachable), which confirms the exclusion here is about what the *technique* requires, not merely about which endpoints discovery happens to reach.

Instead, this slice extends `html_analyzer.py`'s existing form-parsing (`_BoundedHtmlParser`/`_FormRecord`, already used for the password-transport and cross-origin-form-action checks) to track hidden-input fields and flag a POST form with no field matching a recognized anti-CSRF token naming convention. Before writing any code, the token-naming-convention list and the matching approach were surveyed and adversarially stress-tested by two independent lenses: one researching real, current default field names across mainstream frameworks (using live web search, not memory), the other hunting specifically for false positives given the actual parser code, not just the design's prose. Both converged on the same core verdict: the exact-match-not-substring choice for ambiguous short names (`_token`, and the three names added from this review: `form_token`, `form_key`, `_wpnonce`, plus `__token__`) correctly avoids colliding with unrelated one-time-link fields like `reset_token`/`api_token`, and Apache Struts 2's own default field name, the bare word `token`, is deliberately left out of the list entirely because both lenses independently confirmed it collides with exactly that class of field. The review also caught a real gap in the original draft, the matcher only inspected field names and never values, meaning a stale cache or broken template could ship the right field name with an empty or unrendered placeholder value and wrongly suppress the finding; the shipped check requires a non-empty, non-placeholder value before treating a name match as evidence of protection.

Confidence is LOW (this project's weakest tier), severity MEDIUM, and the finding's own description states plainly that absence of a recognized name is not proof of absence of protection: the check cannot see SameSite-cookie-based defenses (already covered separately by `cookie_analyzer.py` under CWE-1275), Origin/Referer validation, a custom header attached by JavaScript, or a `<meta>`-tag-plus-fetch double-submit pattern, and two of the highest-market-share platforms on the web, WordPress and Drupal, both publish their own security guidance recommending developers rename the token field away from the very defaults this check recognizes, specifically so neither an attacker nor a scanner like this one can rely on them. None of this is hedging for its own sake: it is the honest ceiling of what a static, name-based heuristic can ever claim, stated directly rather than smoothed over.

Unit-tested (12 new tests covering the naming-convention matches, the value-placeholder guard, the reset_token/api_token collision-avoidance the exact-match choice exists for, evidence sanitization, and per-form independence), with the pre-existing `html_analyzer.py` suite updated where a test's own scope predated this check (one test now includes a token field so it stays scoped to the password checks it was written to prove, not incidentally exercising the new one). See `docs/audit/active-detection-phase16-csrf-token-heuristic.md`.

## Slice 17: missing authentication (CWE-306) added, with a permit schema change

A seventh post-freeze addition, at the user's continued request for "broken authentication." Unlike every prior post-freeze slice, this one could not stay self-contained inside the scanner package: the user was asked, via a direct question, whether to build the full version (a new signed-permit claim plus CLI/service/executor wiring) or a narrower alternative, and chose the full build.

CWE-287 (Improper Authentication) itself has no safe active-detector shape: proving a target incorrectly *accepts* bad credentials requires actually attempting a login, which is the password-attack territory `ROADMAP.md` already excludes. The concrete, honestly-testable instance is CWE-306 (Missing Authentication for Critical Function): an operator asserts that a specific URL should require a specific authenticated identity, and the detector checks whether it is reachable with no authentication at all. This is the same precision discipline this registry already applies to CWE-639-not-862 for IDOR: the most specific CWE that matches exactly what was proven, not the broader CWE the user's own request happened to name.

Because the detector's candidates are operator-asserted, permit-scoped endpoints rather than crawled or fuzzed values, they needed a new home. A research pass confirmed no existing ad-hoc channel exists for a URL list, and that a direct, bounded claim on the permit itself (rather than a separate plan/repository, the heavier pattern `active.authorization.idor` uses for its own two-identity resource pairs) is the right fit: this claim holds no secrets, needs no independent revocation, and this project's own `authorization_comparison.py` docstring already states the design philosophy this follows ("the smallest clean mechanism"). `CURRENT_TRUSTSCAN_PERMIT_SCHEMA_VERSION` moved `1.3` → `1.4`, replaced outright rather than dual-supported, the same precedent the `1.0`→`1.1` bump set and justified the same way (no deployed old-schema permit to keep compatible). The new field, `missing_authentication_endpoints` (a tuple of `MissingAuthenticationEndpoint`, mirroring `permitted_modes`'s "enum tuple, not bare strings" shape), is enforced bidirectionally and self-containedly inside `TrustScanPermitClaims.__post_init__`: the check ID, a non-empty endpoint list, and a set `authentication_context_id` must all be present together, with no live-repository lookup needed, a stricter and more symmetric rule than IDOR's own analogous cross-check (which only verifies the forward direction, and only once, at issuance time).

Before writing the detector itself, a two-agent adversarial verification pass reviewed the drafted design against real code (not just its own prose) and found one blocking issue and several should-fix issues, all resolved before implementation:

- **Blocking**: unlike `active.authorization.idor`, this detector has no second identity's own baseline to serve as a negative control, so a bare content-fingerprint match promoted straight to CONFIRMED would false-positive on a legitimately public/identical page (a CDN asset, an unpersonalized SPA shell). Fixed by reusing IDOR's own opt-in `owner_marker` mechanism: CONFIRMED now requires both an exact fingerprint match *and* a configured marker present in the anonymous response; either alone is PROBABLE.
- Dynamic per-request content (a CSRF token, a timestamp) would make a genuinely leaking page's authenticated and anonymous bodies differ byte-for-byte, producing a false NOT_VULNERABLE with no fallback. The same marker mechanism fixes this: a marker match on a non-identical response is PROBABLE, not dropped.
- The drafted design assumed a 3xx redirect-to-login would classify cleanly, but `fetch_once` raises `redirect_blocked` for any 3xx unless the caller explicitly passes `allow_redirect_status=True`. Fixed by passing it for both probes and classifying any 3xx from its status alone, before ever reading a body.
- `active.authorization.idor`'s own executor wrapper catches `ActiveDetectionError` around its *entire* per-pair loop, so one malformed resource silently discards every other pair's results, an existing, unfixed, untested gap. This detector deliberately does not repeat it: each endpoint's same-origin check and fetch is wrapped in its own local try/except, isolating a bad entry to that one endpoint's ERROR outcome.
- `active.authorization.idor`/`active.ssrf.callback`/`active.xxe.callback` all skip crawl-mode scans in the executor, each citing page-attribution as the reason. Investigation for this slice found the real, underlying reason is structural, not attribution: `CrawlScanResult` has no scan-wide `findings` field at all (only `ScanResult` does; a crawl report's findings live only inside each individual page in its own `pages` tuple). This detector's candidates were never page-specific to begin with, so there is no page, plausible or otherwise, to attribute a crawl-mode finding to: a stronger reason to restrict to single-page scans than any of its three predecessors had, not a weaker one. Stated explicitly in the detector module's own docstring rather than left as an unexplained copy of the existing pattern.
- Reusing `_apply_active_detection`'s single-identity resolution pattern (resolve once, up front, outside any per-candidate loop; let `AuthenticationContextError` propagate as a scan-level `TrustScanRuntimeSafetyError` rather than being caught per-endpoint) was confirmed as the correct, already-proven-safe precedent, not a new risk to design around.

A new, distinctly-named detector-dispatch category, `FIXED_ENDPOINT_ACTIVE_CHECK_IDS`, was added to `active_detector_registry.py` rather than overloading `COMPARISON_ACTIVE_CHECK_IDS`: that category's own docstring defines "comparison" specifically as IDOR's two-identity, resource-*pair* correlation, a shape this detector (one real identity vs. no identity, flat endpoints, never pairs) does not share. `KNOWN_ACTIVE_DETECTOR_IDS` is the union of all four categories now, and `test_active_detector_registry.py`'s sync assertions were extended to check all pairwise disjointness, not just the original three.

Registered, contract-synced, and unit-tested at every layer: the permit-claim contract (`test_trustscan_permit_contract.py`, 17 new tests: the `MissingAuthenticationEndpoint` dataclass, its `to_dict`/`from_dict` round trip, the bidirectional binding rule's every path, the maximum-10 bound, JSON submission round-tripping, fingerprint sensitivity to the new field); the detector itself (`test_missing_authentication_detector.py`, 12 new tests: CONFIRMED requiring both signals, PROBABLE for either signal alone, the redirect/denial/generic-200 NOT_VULNERABLE paths, INCONCLUSIVE on baseline failure, per-endpoint ERROR isolation, anonymous-probe identity isolation, evidence sanitization, budget/cancellation); and, unlike every detector added since the v1 freeze, a true end-to-end test (`tests/integration/test_missing_authentication_e2e_lab.py`, real HTTPS fixture, real permit → job → worker → executor → report pipeline) proving a genuinely vulnerable endpoint reaches CONFIRMED and a properly-gated endpoint and an inactive permit both produce zero findings. Not yet run against a live/public target. See `docs/audit/active-detection-phase17-missing-authentication.md`.

## Slice 18: real-network validation for the five detectors that lacked it

At the user's request ("do real-network validation for the five detectors next"), this slice closes the one real-network-validation gap every detector added in Slices 12-15 shared (path traversal, command injection, XXE, open redirect, LDAP injection): each got a purpose-built local fixture, exercised over real sockets, mirroring the established pattern from the original four detectors' own `test_active_xss_reflected_live.py`/`test_sqli_error_detector_live.py`/`test_ssrf_callback_detector_live.py` files. This is real-network validation only, not the separate, still-outstanding true end-to-end (CLI → API → worker → executor → report) or live/public-target claims each detector's own row above still states plainly as not done.

Built as five independent, parallel efforts (one per detector), each required a genuinely vulnerable route and a genuinely correct safe route, not a canned response standing in for either:

- **Path traversal**: a real temporary directory on disk; the vulnerable route's `os.path.join` plus `open()` genuinely walks out of it and reads the real `/etc/passwd` already on whatever machine runs the test. This surfaced an honest, unforced result: because a successful traversal read and a successful intended read both return HTTP 200, the detector's own `_classify` lands on PROBABLE, not CONFIRMED, for this fixture shape (`baseline_status == diagnostic_status`), so the test asserts either outcome rather than forcing one that reality did not produce.
- **Command injection**: `subprocess.run(..., shell=True)` for the vulnerable route (a real shell genuinely splits the diagnostic payload on `;` and `#`) versus `shell=False` with an argv list for the safe route (the same string arrives as one inert argument). A third route that reflects the raw, unexecuted value into an error message proves the detector's own marker-plus-payload-absence check for real, the exact false-positive shape this detector's classification logic exists to rule out.
- **Open redirect**: an unconditional `Location: <raw value>` route versus a fixed-destination route, plus a route that renders the marker host as ordinary page text with no `Location` header at all, confirming the CONFIRMED verdict tracks a real status code and header, never a body-text coincidence.
- **LDAP injection**: this detector's own audit doc had explicitly recorded no real directory-backed fixture existed yet, unlike SQLi's real SQLite-backed one. Closed using the pure-Python `ldap3` library's `MOCK_SYNC` strategy, a real `ldap3.Connection` object whose client-side filter compiler (independent of the mocked network transport) was confirmed, empirically, before the fixture was built, to genuinely raise `ldap3.core.exceptions.LDAPInvalidFilterError` on the detector's own diagnostic filter, one of the 13 real signatures this detector's own list already carried, now actually exercised rather than only asserted to exist in the wild. `ldap3` is installed dev-only, into the local venv, for this one test; it is not added to any `requirements*.lock` file or CI configuration, and the test's own import guard skips it gracefully rather than erroring wherever `ldap3` is absent, including this project's current CI.
- **XXE**: Python's own standard-library XML parsers do not resolve external entities by default (a real, well-known fact, not an obstacle routed around by adding a dependency). The vulnerable route uses `xml.parsers.expat` directly with a deliberately-assigned `ExternalEntityRefHandler` that performs a real outbound fetch to the entity's SYSTEM url, mirroring exactly how the existing SSRF live fixture's own vulnerable route works; the safe route parses the identical document with no handler assigned, which is Python's actual secure default, not a simulation of one. Both routes run through the real `CallbackHttpReceiver`/`InMemoryCallbackBroker` SSRF's own live test already established.

No bug was found in any of the five detector modules during this work: every one's real, unmocked behavior against its own fixture matched its own docstring's claims exactly. ## Slice 20: live-target investigation for the detectors that lacked it

At the user's continued request ("do the live-target investigation for the remaining detectors next"), this slice investigates path traversal, command injection, XXE, open redirect, LDAP injection, and missing authentication against the pinned Juice Shop lab container (v20.1.1), the same live target `active.authorization.idor` was already confirmed against. Every finding below is backed by either a live HTTP probe against the running container, or the container's own actual server source read directly with `docker exec ... /nodejs/bin/node -e "..."` (this image ships no shell and no `find`, only the Node runtime, so source was read via short Node scripts rather than assumed from memory of older Juice Shop versions). CWE-79 and CWE-89 already had this done, honestly negative, in Slice 1-3 and Slice 4 respectively; this slice does not repeat that work, only independently re-derived the same structural conclusion for CWE-79 while investigating CWE-78's own shell-execution surface (a pure Angular SPA with zero server-side HTML templating from user input anywhere in the built server has no reflected-XSS surface for either detector to test, confirmed by source, not assumed).

Five of the six are negative for the specific technique each detector uses, each for a distinct, evidenced reason, not a single generic "not found":

- **Path traversal**: a real file-disclosure vulnerability exists (`routes/fileServer.js`'s poison-null-byte extension-filter bypass, confirmed live: `GET /ftp/package.json.bak%2500.md` returns real file content), but the route explicitly rejects any `/` in the requested filename before ever touching the filesystem, so a `..`-sequence payload never reaches it, and the files it can disclose are app-internal fixtures, never `/etc/passwd`-shaped content this detector's signature list would recognize even if one did get through.
- **Command injection**: an exhaustive search of every built server-side file for `child_process`, `execSync`, `spawn(`, or a bare `exec(` found nothing (the one incidental match was `RegExp.prototype.exec()`, not process execution). No shell-execution code exists anywhere in this application.
- **Open redirect**: a real allowlist gates `/redirect?to=`, confirmed live (`406` for an unregistered marker host, a real `302` for a genuinely allowlisted one). This detector tests only for a missing allowlist; Juice Shop's own "Allowlist Bypass" challenge requires exploiting a flaw in a present one, a different technique this detector's fixed-marker probe cannot attempt.
- **LDAP injection**: zero LDAP-related code exists anywhere in the built server (source-searched exhaustively). Juice Shop has no directory-service integration of any kind.
- **Missing authentication**: every anonymously-reachable endpoint checked (`/rest/memories`, `/rest/track-order`, `/api/Feedbacks`, `/file-upload`) is either intentionally public by the application's own design, or a different CWE shape (the memories/photo-wall feed anonymously exposes every user's password hash and deluxeToken embedded in nested `User` objects, a real finding, but CWE-200 sensitive-data-exposure via a legitimately-public endpoint, not missing authentication). This detector's contract needs an operator's genuine intent behind a specific URL; no lab target can supply that on someone else's behalf.

The sixth, XXE, is the significant exception and the most valuable finding of this slice: **a real, live, anonymously-exploitable XXE vulnerability was confirmed**, not merely investigated and ruled out. `routes/fileUpload.js`'s `handleXmlUpload`, reachable at `POST /file-upload` with no authentication at all, parses an uploaded `.xml` file with `libxml2-wasm`'s `XML_PARSE_NOENT | XML_PARSE_DTDLOAD` and an explicitly-registered filesystem input provider ("Grants the WASM sandbox host filesystem access so external entities like `file:///etc/passwd` resolve - required for the XXE challenges," in the source's own words). Confirmed live: a crafted `complaint.xml` with a `file:///etc/passwd` SYSTEM entity, uploaded anonymously, returned the container's actual `/etc/passwd` content embedded in the HTTP 410 error body. This detector cannot confirm it anyway, for two independent structural reasons: it never inspects response text by design (the vulnerability here manifests entirely in the response body), and it only ever sends network-callback SYSTEM URIs, which a WASM sandbox with no socket capability has no way to resolve even if the response were inspected. The vulnerability is real; the gap is a detection-technique variant (in-band file disclosure) this detector was deliberately never built to cover, named plainly in the module's own docstring as excluded v1 scope well before this slice, not discovered as a surprise.

No detector code, executor code, or test file was changed this slice; it is investigation and documentation only. See each detector's own audit doc for the full evidence trail.
